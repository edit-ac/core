# Internal web feature ledger

This is the WFE-3.1 feature inventory, not an alpha or release receipt. The machine-readable inventory is [features.json](../../fixtures/product-scenarios/web/features.json). It retains the original requirement/case IDs, current public entrypoints, independent behavioral oracles and exact owning proof digests. A proof group always names original executed child receipts, including children reused by an aggregate checkpoint.

Run from `core/` with the repository Node version:

```sh
node scripts/check-web-feature-ledger.mjs ../architecture/evidence/web-feature-first-20261018/wfe-3.1/applicability.json
```

Exit zero means every indexed feature has applicable evidence and no declared coverage gap. Exit one preserves the unresolved paths/cases in the JSON report. The checker does not execute features or close a roadmap gate. Public API text references support navigation; they are not type or behavior tests. It authenticates full recorded source manifests, each original runtime receipt, nonzero case accounting and the installed package bytes. Product evidence additionally compares the recorded SDK revision with current engine/package inputs. It never waives changed inputs. A passing owner receipt cannot establish a complete current product when another required proof is missing.

## Owner returns and source applicability

PRIMARY owns engine/Session/storage/ABI, ordinary browser editing and baseline assistance/touch. PARALLEL owns rich presenters and optional format/extension controls. Read existing pending WEX-1.3/WEX-1.4/WEX-2.1 requests at a safe integration checkpoint; do not modify the active other-lane checkout. WEX-2.2 waits only for its exact portable owner return, without blocking other features. Missing source-compatible proof stays open even if an earlier aggregate roadmap says COMPLETE.

The pinned product proof is PWE-1.5: 93 cases proven by 33 executions plus 60 exact child reuses in its historical aggregate. This ledger indexes the nine original child receipts instead of treating reused cases as fresh execution. Subsequent SDK changes require current source applicability and, where affected, the existing canonical product dispatcher. Feature-source authenticity and local-main applicability are separate evidence.
